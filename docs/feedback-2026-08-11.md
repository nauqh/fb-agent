## A. Regressions — things that used to work, or look like they should

### A1 `[x]` Padding and text size appear to do nothing — **done 2026-08-11**

**Confirmed, fixed, and verified in a browser.** The smoking gun is that
History Retraced *already had the overrides saved*: `GET /layout?page_id=1`
answers `overridden: [text_font_size_px, text_padding_*]` with padding `0` on
all four sides and font size `30`. The client changed those settings, they were
stored correctly, and the write path was never at fault — the Review screen
simply did not read them.

`ComposedImage` now takes the resolved layout and the Page, and draws
`full_overlay` as well as `card`. `LAYOUT` in `lib/fixtures/pages.ts` is gone,
along with the dead `lib/api/config.ts` that duplicated `lib/api/layout.ts`.
Driven in a browser at `/review/14`: the panel renders padding 0 as the baked
PNG beside it always did.

Cause (2), stale composites, is closed by decision — see *Decisions taken*.
Cause (3), the switcher, is answered by keying the layout query on the
**draft's** `page_id` rather than the switcher's.

Two things fixed on the way that were not in the report:

- The watermark drew a red "no watermark asset" box for any Page without a
  committed file — the normal state for eight of the ten, which publish an
  upload or their name as text. It now follows `page.watermark()`.
- The mark hung from `edge_margin_ratio` rather than `watermark.top_ratio`.

> "Padding doesn't seem to be working anymore — changing the setting doesn't
> seem to make any difference. It looks like the same might be happening with
> text size as well."

The write path was never broken. `PATCH /layout` accepted all four padding
fields and `text_font_size_px` (`api/app/routes/config.py:139`), stored them on
`page_layout`, and the compositor read them — so **every post generated during
the complaint already had the requested padding baked into it.** The Global
screen's own sticky preview read them too. Only the Review screen did not.

Three separate things could produce "no difference". What each turned out to be:

1. **The Review preview ignored them outright — this was it.**
   `composed-image.tsx` hardcoded `padding: "6% 4%"` and
   `fontSize: "clamp(10px, 4.1cqw, 19px)"`, and every other value came from the
   frozen `LAYOUT` fixture, which has nothing per-Page in it. CSS percentage
   padding resolves against *width* on every side, so `6%` was 54px where the
   compositor draws 15px. **Fixed**: `ComposedImage` takes the resolved layout,
   and the fixture is deleted so no second copy can drift again.
2. **Existing drafts are not redrawn when the layout changes.** Still true, and
   **closed by decision** rather than by code — see *Decisions taken*. In
   production a draft is published or rejected before a layout change reaches
   it, so the stale window is theoretical.
3. **The Page switcher.** Was a real hazard: the layout query could name a
   different Page than the draft on screen. **Fixed** by keying it on the
   draft's own `page_id` rather than the switcher's.

Verified in a browser, which is what settled it — the padding values were
already stored, so no amount of reading the write path would have shown the
fault.

## B. Screens and controls that existed in the old app and were not ported

### B1 `[ ]` Overview page — L

> "Where is the Overview page now? I'd like to be able to see post performance
> there and save the top-performing posts for future reference/reuse."

Not built. The old app has the whole thing:
`social-agent/src/components/facebook-agent/overview-panel.tsx`,
`viral-posts-panel.tsx`, `hooks/use-saved-viral-posts.ts`,
`lib/facebook/overview-performance.ts` and `overview-post-stats.ts`, behind
`api/facebook/overview/` and `overview/performance/`.

Two halves, and they should be two commits:

- **Performance** — read-only, from Metricool analytics. `sources/metricool.py`
  already speaks to the analytics API for competitor posts; this is the same
  auth against our own Pages.
- **Saved top posts** — the only half that needs a table. A saved post is a
  reference kept on purpose, so it outlives the analytics window it came from;
  a row, not a cached read. This is new schema and therefore an Alembic
  revision.

### B2 `[ ]` Manual page — S

> "It looks like the Manual page no longer exists. Could we move this section
> back to the Manual page?" — screenshot shows the *topic* field.

The section they mean is the "Tick a source, or write from a topic" strip
(`cart-panel.tsx:86-104`). It was deliberately folded into the Sources dock —
the reasoning is in the file's docstring, and it was correct for a Cart-first
flow. The client wants it as a destination of its own, with room to grow ("I
have some future plans for the Manual page").

Cheapest honest shape: a `/manual` route with the topic field and the Generate
button, and the topic half removed from the Cart dock so there is one place to
type a topic. Add it to `sidebar.tsx:48` `LINKS`.

Confirm with the client before removing it from the dock — they said "for now I
don't need anything beyond this", which reads as *move*, not *duplicate*.

### B3 `[ ]` Regenerate Hook / Caption / First Comment — M

> "I don't see an option to regenerate these anymore. Could we bring that
> back?"

Correct, gone. The writer produces all fields in one call
(`generate._run_one:157`) and the only regenerate in the app is the hero
(`draft-detail.tsx:253`, `POST /drafts/{id}/image?new_hero=true`). The old app
had per-field regeneration —
`social-agent/src/components/facebook-agent/regenerate-field-control.tsx` and
`lib/facebook/draft-regenerate.ts`, with a `RegeneratableField` union.

New endpoint `POST /drafts/{id}/regenerate?field=hook|caption|first_comment`.
The one real decision is whether a regenerated hook triggers a recomposite —
it must, `hook` is in `DRAWN_FIELDS` — and whether the other fields are
regenerated in context of the ones being kept. They should be, or a new caption
will not match the hook above it.

### B4 `[~]` Circular inset — the old app's full flow — M/L

**Two of the three pieces are done (2026-08-11).** The per-Page defaults are on
Global as a *Circular inset* group — default size, border width, border colour —
with a hatched stand-in disc drawn in the sticky preview, because ring width is
the one setting nobody can judge from a number. The per-draft override is in the
review drawer as a *Ring* control, with an explicit "Use the Page's" reset that
is the only way back to null.

`Draft.inset_border_width_px` and `inset_border_color` are nullable columns
(revision `3749e016826e`), null meaning "the Page's". Verified in a browser on
draft 14, the one draft carrying an inset.

Two defects found and fixed while building it, neither of which the tests would
have caught because a wrong ring still produces a perfectly valid PNG:

- **A zero-width border filled the disc.** Pillow reads `width=0` as *fill the
  shape*, so "no border" — the client's own first option — would have painted a
  solid disc of the border colour over the picture.
- **A thick ring was clipped.** The ring is a stroke centred on the disc edge,
  so half falls outside, and the canvas grew by a constant `ring_pad_px: 3` —
  enough only for the file's 2px border. At the old app's 48px maximum the
  overhang is 24px. `PortraitLayout.ring_pad` derives the padding now.

Both are pinned by tests (`test_generate.py`, "the inset's ring").

**Still open: the AI-generated inset**, the third piece below — Upload/Generate
tabs, `Draft.inset_prompt`, and a `POST /drafts/{id}/inset-generate`.

> "Could we have the following options back? No border, Border colour, Border
> size, AI-generated image. Mixture of on the settings page and on the review
> page."
>
> Follow-up, 2026-08-11: *"The client want to further customise the inset,
> similar to the old app flow."*

Today the inset is upload-only, with a size slider and a drag handle
(`draft-detail.tsx:452-529`). Border width and colour exist only as *layout*
values — `portrait.border_width_px` and `portrait.border_color` in `layout.yml`,
and as columns on `page_layout` — and the Global editor exposes no control for
either; the `portrait` group is simply absent from `layout-editor.tsx`.

**The follow-up changes the design.** The old app held border width, border
colour, diameter, centre *and* the generation prompt **per draft**, on
`ai_metadata.portraitInset` (`portrait-inset-shared.ts:parseDraftPortraitInset`,
and the dialog at `circular-inset-dialog.tsx:563-680`). Putting them only on the
Page — which is what the first pass of this plan said — would be a narrower
control than the client had before, and the picture is exactly the thing that
varies per post: a dark portrait wants a light ring, a bright one wants none.

So the shape is the one this codebase already uses for `inset_size_px`: **the
layout is the default, the draft overrides it, null means inherit.** That is
also the honest reading of "a mixture of on the settings page and on the review
page".

Three pieces:

- **Per Page — Global → Composed Image.** A Portrait group: default diameter,
  border width (0 = no border), border colour. All three columns already exist
  on `page_layout`, so this is UI only, plus `portrait_*` entries in
  `LayoutPatch` on the web side. **S.**
- **Per draft — the review drawer.** New nullable columns
  `Draft.inset_border_width_px` and `Draft.inset_border_color`, each null
  meaning "the Page's". `compositor.Inset` grows the two fields and
  `circular_portrait` prefers them over `layout.portrait`. Bounds from the old
  app: border 0–48px, diameter `min_px`–`max_width_ratio × width`. Alembic
  revision required — the suite builds its schema with `create_all` and cannot
  catch a missing one. **M.**
- **AI-generated inset.** Upload/Generate tabs, as
  `circular-inset-dialog.tsx:490-560` had them, with the prompt seeded from the
  draft's topic and a `POST /drafts/{id}/inset-generate` behind it. Needs a
  `Draft.inset_prompt` column so a regeneration does not lose the wording.
  Note `models.py:552` currently states outright that nothing generates the
  inset, and `layout.yml`'s `portrait` block says the same — **both comments
  become wrong and must be rewritten, not left to rot.** **M.**

Worth copying from the old dialog, because each was a deliberate choice: a
number input beside every slider (a slider cannot hit 137px), the live card
preview behind the controls rather than beside them, and border width `0`
rendering as a disc with no ring rather than a hairline.

## C. Generation options

### C1 `[ ]` Choose the template when generating, and switch it at review — M

> "When generating, I don't see an option to choose between the Card template
> and the Full Overlay template… also useful to have the same option during the
> review stage, so we can switch between the two before publishing."

Both templates exist (`layout.yml: template`, and the full-overlay path in the
compositor with its headline badge, commit `62586da`). The choice is currently
**per Page**, not per draft: `page_layout.template`, set on Global.

Making it per draft is a schema change — `Draft.template: str | None`, null
meaning "use the Page's" — plus threading it through `layout_for.resolve`,
which today takes only a `page_id`. Then:

- Generate: a two-way toggle beside the Generate button, defaulting to the
  Page's.
- Review: the same toggle in the drawer; changing it recomposites, which is
  free (the hero is reused).

Note the Review preview cannot currently draw `full_overlay` at all —
`composed-image.tsx` only knows the card form. Same root cause as **A1**, and
worth fixing in the same pass.

### C2 `[ ]` Generate without an image — S

Nothing supports this. `build_image` returns a warning when there is no hook
and otherwise always produces a hero (`generate.py:216`). A text-only post is a
different publish payload too — `metricool.build_body` always sends
`media: [image_url]`, and `publish_draft` refuses a draft with no composite
(`routes/drafts.py:375`).

Smallest shape: a `no_image` flag on the generate request, stored on the Draft,
which skips `build_image` and lets publish send a body with no `media`. Test it
against Metricool before believing it — a Facebook post with no media may be
refused by the scheduler.

### C3 `[ ]` Use the image the RSS feed supplied — M

`SourceItem.image_url` is already carried through from the feed
(`models.py:488`) and the source cards already display it — so the picture is
in hand, and this is purely "fetch that URL and use it as the hero instead of
buying one from Gemini".

Two things to get right: the hero is written into our own bucket rather than
hot-linked (a feed image can vanish, and Facebook fetches at publish time —
same trap the Metricool notes in `CLAUDE.md` describe), and the fetched image
has to be resized to the plan's `hero_height_px` like a generated one is.

This is the cheapest of the three generation options and it saves money on
every run that uses it.

## D. Publishing and scheduling — the largest piece

### D1 `[ ]` What does Approve do, and should it exist — M

> "What exactly does the Approve button do? Does it simply remove the post from
> the queue? If so, I'm not sure we actually need an Approve button — perhaps
> we can just have the scheduling options directly."

The client's reading is right. Approve sets `status = approved`
(`routes/drafts.py:428`), which takes the row out of the Review queue and
nothing else. It is explicitly reversible (`unapprove`), and publish does not
require it — `publish_draft` refuses only a republish, a FAILED draft, and one
with no composite.

So Approve is a queue movement with no consequence. Recommend removing it and
letting the three scheduling actions in **D2** be what takes a draft out of the
queue. Keep `DraftStatus.APPROVED` in the enum for the rows that already carry
it; stop writing it.

Reject stays — it is the decision that *isn't* publishing.

### D2 `[ ]` Publish Now / Schedule / Schedule Next Available Slot — M

Today there is one Publish button with a datetime field beside it
(`draft-detail.tsx:711`), where an empty time means "as soon as Metricool will
take it" (`metricool.publication_date`, floor of now + 2 minutes). So *Publish
Now* and *Schedule* already exist as one control; this is mostly a matter of
making them two obvious buttons rather than a field the operator has to
understand.

*Schedule Next Available Time Slot* is the new one, and it depends on **D3**.
It means: take the Page's configured slots, walk forward from now, and pick the
first that has nothing in Metricool's planner. The planner read already exists
(`publisher.list_scheduled`, used by the Schedule screen), so the collision
check is a read we already do — no local schedule state, ADR-0001 holds.

### D3 `[ ]` Time slots in Page Settings — M

> "In Page Settings, we should be able to create as many time slots as needed
> and modify the time of each slot."

New table — `page_time_slot(page_id, time_of_day, weekday?)`. Ask whether slots
are per weekday or the same every day before building; the feedback does not
say, and the answer doubles or halves the UI.

This is **not** a violation of ADR-0001. A slot is a *policy* ("we post at
08:00 and 19:00"), not schedule state; nothing here mirrors what Metricool
holds. Worth saying so in the ADR itself so the next person does not have to
re-derive it.

Times are `Asia/Ho_Chi_Minh`, like every other clock in the app.

### D4 `[?]` First comment delay — M, blocked on a spike

> "I don't want the first comment to be published at exactly the same time as
> the post… No delay / Delay by X minutes."

**This is the item most likely to be impossible as asked.** We do not publish
the first comment — Metricool does, from `firstCommentText` in the scheduler
payload (`publish/metricool.py:141-152`), and the API exposes no delay field
for it. The old app could offer a delay because it published through **Postiz**,
whose payload takes a per-item `delay`
(`social-agent/src/services/postizService.ts:326-330`, default 5000ms).

Spike before estimating: ask Metricool's scheduler for a delay parameter, and
verify against the live API rather than the docs — their documentation has been
wrong twice already in this repo (the normalize endpoint's re-hosting claim,
and the `mediaId` form).

If there is no delay field, the three options are:

1. Publish the comment ourselves via the Graph API after the post lands. Needs
   a page access token, a way to know when Metricool published, and a delayed
   job — the app has no worker and one replica by design. Real cost.
2. Move publishing to Postiz, as the old app did. Large, and re-opens a
   decision already made.
3. Tell the client it is not available through Metricool. Cheapest, and honest.

Recommend the spike, then (3) unless it turns out to be free.

## E. Removals

### E1 `[ ]` Drop hashtags — S

> "I don't think we need hashtags anymore, so we can remove this."

Touches five places: the `hashtags` column (`models.py:544`), the writer's
schema and `validators.normalise_hashtags`, the `DraftEdit` field and its
normalise branch (`routes/drafts.py:99,140`), `_post_text` which appends them to
the caption (`routes/drafts.py:416`), and the Hashtags field plus the Facebook
preview in the web app.

Leave the **column** in place and stop writing to it, rather than dropping it in
a migration — 17 drafts carry values, and a dropped column cannot be undone if
the client changes their mind. Remove the UI, the writer output and the
caption append. Say plainly in the commit that this is a UI/behaviour removal
and not a data one.

## Decisions taken — 2026-08-11

Answered by the operator after the first read of this document. Recorded here
rather than only in the items, so a later reader can see what was chosen without
reconstructing it from the prose.

- **A1, stale composites.** Existing drafts keep the PNG they were baked with.
  No redraw button, no recomposite on save. The reasoning is that by the time a
  layout change lands, a draft in production has already been published or
  rejected — so the stale window is theoretical. One line on the Global card
  says so; nothing else is built.
- **B2, the Manual page.** *Move*, not duplicate. The topic field leaves the
  Sources dock, which keeps only the Cart.
- **D3, time slots.** The same times every day. A flat list — 08:00, 13:00,
  19:00 — with no weekday dimension. Next available walks forward through days
  at those times.

## Parked — not being worked on

### P1 `[?]` AI-sourced real photographs from the internet — L

> "It would be great if we could let the AI source a suitable real-life image
> from the internet when needed, for both the hero image and the circular inset
> image." — `fbtool1.docx`, under *Additional*

**Deliberately out of the plan. Do not start it.** Kept here in full so the ask
is not lost, and so the next person does not re-derive why it is not in F.

Gemini cannot browse. This is an image *search* feature wearing an AI hat: it
needs an external API — Google Programmable Search, Bing Image Search, or a
stock provider — plus a judgement the app currently never makes, which is
**image rights**. A generated hero raises no licensing question. A photograph
pulled off the web, published to a page with an audience, does — and we would be
answering it silently on the client's behalf, once per post.

The two shapes, if it is ever picked up:

- **Licensed stock** (Unsplash / Pexels, free APIs). Clear commercial-reuse
  licence. Narrow where it matters most — named historical people and events are
  most of History Retraced, and stock has very little of them.
- **General web search.** Finds the actual photograph. Every result carries an
  unknown owner.

**Check this first, before spending anything.** Two items already in the plan
overlap it heavily, and between them they may be the whole of what was actually
wanted:

- **C3** — use the picture the RSS feed already supplied. A real photograph, no
  new service, no cost, and it carries the rights the publisher already carried.
- **B4** — the AI-*generated* inset. Note the doc asks for this separately, in
  the Circular inset list, and generated is not sourced. It is a straight port
  of the old app's dialog and raises none of the above.

If "I want a real photo rather than an AI-looking one" was the intent, C3 and B4
cover it and this can be dropped outright.
